一、《大象》实测诊断：问题比"重叠"更结构性

量化结论：手机屏 390px 宽下，9 行谱共 269 个音符，其中 245 个（91%）的实际占位宽度低于可读下限（需 ≥15.5px，实际最小 9.9px）。自适应缩放已压到 0.45 的下限仍放不下整行——每一行的行尾都被裁切，横向滚动重新出现。这不是"个别音符重叠"，是整首谱在手机上不可用。
▲ 当前渲染实拍（390px 手机宽，第 1–5 行）：行① 尾部的和弦 5̇ 已被切出屏幕；行③ 连续十六分音符的减时线粘连成一片；八度点小到难以分辨。

渲染器的三个技术成因

  1. 宽度靠常量估算，不测真实字宽：每个音符占位是写死的（四分 34px / 八分 27px / 十六分 22px），技法字、八度点、和弦叠音、附点全按比例偏移画在格内——格子一旦被压缩，附加元素必然越界压到邻居。
  2. 自适应缩放有下限：zoom≥0.45 的保护下限在超密行（④行 40 音、自然宽 1228px）面前失效，结果就是裁切＋横向滚动。
  3. 没有"按拍定量"：音符在格内居中，格宽与时值不成比例——十六分和四分在视觉上没有快慢对比，读谱的人（孩子）看不出节奏骨架。
关键判断：渲染器救不了密度。一行 40 个音符塞进一屏，物理上不存在可读解。正确解法是把「全曲浏览」和「乐句练习」分成两个视图——扬琴本来就分句练，练习视图一次只放大 1–2 小节，密度问题自动消失，而且更符合教学法。

主题（10–29）前二句快速十六分音符；后二句双音；第五句单轮音行③–⑥（双音段＋轮音长音段）吻合

三、专业简谱排版调研

调研了国内外可用的简谱（numbered notation）排版方案，共 6 个候选：

方案性质技术栈授权嵌入我们的产品
Sparks NMN[4][5]文本语言 → 简谱渲染，核心基于 Web，样式参照中国义务教育音乐课本TypeScript，浏览器直接运行Apache-2.0（已查 LICENSE 原文，可商用可嵌入）最优候选。但无 npm 包，需源码引入；双音/坐标待验证
jianpu-ly + LilyPond[6][7]Python 预处理器 → LilyPond 排版，出版级质量Python + LilyPond 桌面编译GPL / Apache（两镜像不同）排版质量天花板，但产物是 PDF/SVG 静态图——拿不到音符坐标，标注功能做不了；不支持扬琴轮音以外的部分技法，需 workaround
jp-word / MusicWriter / 来音制谱[8]所见即所得打谱软件（国内）闭源桌面软件闭源/付费只能当人工录谱的辅助工具，无法嵌入产品
MuseScore + 简谱插件线谱转简谱C++/QtGPL插件已断更，操作复杂[8]，不适用
xml2jianpu 等转换器MusicXML → 简谱JS各异不支持多声部[8]，扬琴双音直接出局
自研渲染器（现状）SVG 逐音符绘制原生 JS自有唯一优势：每个音符的坐标完全可控（点音符标注功能依赖这一点）

Sparks NMN 深入评估

为什么它是最优候选：① 排版目标是" readability 优先"，明确写了"重视乐谱的可读性和空间感，对各种元素设置有差异的大小和间距"[4]——正是我们缺的东西；② 核心是 Web/TypeScript，与我们原型同栈，浏览器直接跑，不需要 LilyPond 那种服务端编译；③ Apache-2.0 无传染性；④ 支持播放（可听音校对，反哺"不准"问题）；⑤ 文本格式与我们的 JSON 谱面数据结构接近，写一个 JSON→NMN 转换器是低成本可逆的。

三个必须先验证的问题（决定成败）：

  1. 双音/和弦：扬琴《大象》大量双音。官方示例里出现 (2^1^) 这类写法疑似双音[5]，需实测确认渲染质量与八度点处理。
  2. 音符坐标：老师"点音符做标注"是产品核心交互。Sparks NMN 若不暴露每个音符的命中区域/坐标，标注功能要另想方案（如在其渲染结果上叠一层透明点击层，按音符索引映射）。
  3. 技法符号：轮音（扬琴最核心技法）、拨、顿音、上滑——简谱通用引擎不一定内置，可能要用 Unicode 符号或自定义 extension。

四、建议路线

优先级事项产出成本
P0《大象》双引擎对比试验：写 JSON→Sparks NMN 转换器，把已录的 9 行喂给它渲染，与自研渲染器同屏对比（同一内容、同一屏宽）；同时验证上面三个问题对比截图 + 可行性结论1 天
P0乐句分句：练习视图按乐句（1–2 小节）放大呈现，全曲视图保留小字浏览——无论用不用 Sparks NMN 都要做密度问题消失1 天
P1校对工作流：原书页截图与渲染结果并排，逐行点"通过/有误"，曲子带 verified 状态位——"不准"的唯一根治法数据可信度闭环半天 + 你的人力
P1用官方曲目表核对 84 首元数据（改编者/级别/类型）[1]元数据可信半天（脚本可比对大半）
P2若 P0 试验通过：逐步把渲染层切到 Sparks NMN，自研渲染器保留为标注坐标层的兜底排版质量整体升级3–5 天
一个要先想清楚的取舍：换渲染引擎后，"点音符标注"的交互要重新接。若 Sparks NMN 坐标方案走不通，fallback 是"文本选段标注"（按 行-小节-音位 选择而非直接点音符）。建议 P0 试验时把这个一并测掉，再决定全量切换与否。
